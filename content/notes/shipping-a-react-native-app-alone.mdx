I budgeted six weeks to build my first React Native app on my own. The code took
about three. The other three went somewhere I had not planned for at all.

## What I thought the work was

Screens, navigation, state, an API. That part went roughly as expected. Expo
removed most of the native build friction, TypeScript caught the mistakes I
usually make, and by the end of week three I had something I was happy to demo.

Then I tried to put it in front of people.

## What the work actually was

**Provisioning.** Certificates, identifiers, provisioning profiles, and the
particular way they expire at the least convenient moment. EAS handles most of
this now, but you still need a working mental model of what it is doing, because
when it fails the error is rarely about the thing that is actually wrong.

**Store review.** My first submission was rejected for a privacy manifest that
did not declare why the app read location data. My second was rejected because
the demo account I supplied had expired. Neither was a code problem. Both cost
several days of waiting.

**Update strategy.** Native releases go through review; JavaScript bundles can go
out over the air. Deciding which changes belong in which channel — and making
sure an OTA update can never land on a native build that cannot run it — is a
design decision, and one that is much cheaper to make before launch than after.

**The things nobody demos.** Deep links, push notification permissions, what
happens on a cold start with no network, and how the app behaves when the OS
kills it in the background. All of it invisible in a demo. All of it the
difference between an app people keep and an app people delete.

## What I would do differently

Submit a skeleton build to review in week one. Not to ship it — just to find out
what the process objects to while there is still time to react. Everything I lost
time to was discoverable early and expensive late.

The code is the part you can estimate. Budget for the rest.
